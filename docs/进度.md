## M6 的两次验证结果

**生产模式验证**（`npm run build` + `npx electron .`，即 `file://` 加载）—— 查出并修掉一个真 bug：

打开 EPUB 报 `Cannot read properties of undefined (reading 'currentLocation')`。根因是 epub.js 的 `renderTo()` 立刻返回 Rendition，但 `manager` 要稍后才由 `Rendition.start()` 创建；`display()` 之类走 rendition 的队列所以排在 attach 之后，而 `currentLocation()` / `resize()` / `themes.*` 直接访问 `manager`、不排队。**这是个只在特定时序下暴露的竞态**——开发模式下 `load()` 里的几次 await 恰好给了队列足够时间，从 M3 到 M5 一直没踩到。

这个 bug 正好印证了「先验生产模式、再配打包器」这个顺序的价值：若先配打包器再验，会被误当成打包问题去查。

**安装包验证**（人工）—— 安装不弹向导、不需管理员权限，图标正确，主链路正常，免安装版可用，**卸载后 `%APPDATA%\Mark Reader` 里的书保留**。

## 未决事项

按重要性排：

1. **尚无自动化 E2E**。M1–M6 的端到端验证全是手工做的。§6.5 规划了 5 条 Playwright 场景（P0 两条：导入 EPUB、位置恢复），CI 的 `workflow_dispatch` 档位里也给它留了位置——但需要先把测试基建搭起来，是一整轮独立的活
2. **表格兜底始终没在真机上看过效果**。代码在 `EpubEngine` 的 `rendition.hooks.content` 里给每张表包了 `overflow-x` 容器，但那个 hook 是**每章渲染时触发一次**，要翻到有表格的那一章才看得到。`tests/fixtures/wide-table.epub` 的表格在第二章
3. **M2 只验证了「删除 → 取消」**，没验证过真的删掉之后重启（删除路径本身的文件清理有单测覆盖）
4. **TXT 的两处近似**：页码换算是页粒度（不是字符粒度），`applySettings` 的位置保持同样近似，误差上限都是一页宽度。两者在代码注释里写明了取舍
5. **无签名**：安装包没有代码签名证书，Windows 会弹 SmartScreen 警告。个人自用可接受

## 本机环境注意事项

- **`.npmrc` 里的 `ELECTRON_MIRROR`** —— Electron 二进制从 GitHub Release 直连实测 15 分钟无进展
- **`package.json` 里的 `allowScripts`** —— npm 11 默认拦 postinstall，缺这条 Electron 二进制不会下载。**加新依赖时留意是否需要再放行**
- **Node 24** —— 技术方案 §6.5 原写 20，但 20 已于 2026-04 EOL
- **`gh` 已装但要带全路径**：`"/c/Program Files/GitHub CLI/gh.exe"`。会话若在安装前启动，PATH 里没有它
- **`scripts/render-icon.ps1` 必须存成带 UTF-8 BOM** —— PowerShell 5.1 把无 BOM 的 .ps1 当 ANSI 读，中文注释被解码成乱码后会污染后续行，表现是脚本顶部的变量莫名其妙变成 null

## 开发时可用的几样东西

- **渲染进程 console 转发**：只要应用没被打包就会把渲染进程的 console 打到 stdout（`src/main/index.ts`）。M2–M6 修的每个真问题都是靠它发现的，**动它之前想清楚**
- **样本**：`tests/fixtures/` 有 6 个样本 EPUB 与生成器；TXT 样本用 `iconv-lite` 现场造即可
- **图标生成器**：`npm run make:icon`
- **测试目录分层**：`tests/main/`（node）与 `tests/renderer/`（jsdom，按文件加 `// @vitest-environment jsdom`）。`tests/renderer/makeApi.ts` 是 `MarkReaderApi` 的共用测试替身
- **不要在单元测试里拉 epub.js** —— 一个文件要多花 40 秒
