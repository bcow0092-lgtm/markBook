# M6 打包 实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 产出可双击安装的 NSIS 安装包与免安装版，并确认打包后主链路照常。

**Architecture:** 本里程碑的风险不在打包器，在**生产模式下的 origin 变化**。开发时渲染进程从 `http://127.0.0.1:5173` 加载，打包后从 `file://` 加载 —— 而 M2–M5 的全部验证都在开发模式下做的，`app://` 在生产 origin 下能不能用从没验过。因此**先验生产模式，再配打包器**：`npm run build && npx electron .` 就已经是 `file://` 加载，不需要打包器介入。风险最早释放，也最容易定位。

**Tech Stack:** electron-builder + NSIS。

**Spec:** [技术方案文档.md](../../../技术方案文档.md) —— 本计划实现 §1（选型表里的 electron-builder + NSIS）、§5.1 的风险（「打包后 `app://` 协议路径解析差异」）、§6.5（CI 的 `workflow_dispatch` 档位）。前序里程碑见 [M1](./2026-09-19-m1-骨架与风险验证.md) ～ [M5](./2026-09-25-m5-设置与打磨.md)。

## Global Constraints

- 平台：Windows 桌面应用。CI runner 必须 `windows-latest`。
- Node 24。`vite` 锁 `^7`、`@vitejs/plugin-react` 锁 `^5`。
- **不要动 CSP**（§2.2 每条都是实测调出来的）。生产模式下若 CSP 出问题，先确认是不是 origin 变化导致的，不要直接放宽策略。
- **不要为了打包成功而关掉 `webSecurity`** —— 那会把 §2.2 的整套安全基线推翻。生产模式若因 origin 受阻，正解是让渲染进程也走 `app://`（见 Task 1 的退路）。
- 交付前 `npm run verify` 必须全绿。每个任务结束前必须 commit。
- 注释与提交信息用中文，代码标识符用英文。

## 与设计文档的差异

1. **Task 1 在生产模式下先验、再配打包器。** §7 把「打包」与「打包后回归」都放在 M6，但没规定顺序。实际上生产模式不需要打包器就能验，放前面能让最大风险最早释放。
2. **渲染进程的 console 转发条件要改。** 现在是「`ELECTRON_RENDERER_URL` 存在时才转发」，也就是只在 dev 下转发。生产模式没有它，**验证时终端里什么也看不到** —— 而这正是本次最需要的信息来源。改成「只要应用没被打包就转发」。
3. **如果生产模式下 `app://` 因 origin 受阻，退路是让渲染进程也走 `app://`。** 那时页面 origin 变成 `app://local`，与书籍资源同源，跨源问题自然消失。这比关 `webSecurity` 干净得多，但会改动 `protocol.ts` 与 `electron.vite.config.ts`，属于 Plan B。

### Task 1: 生产模式验证

> **本任务不产出功能代码**（除非验证失败需要修）。产出是结论。

**Files:**
- Modify: `src/main/index.ts`（console 转发的条件）

**Interfaces:**
- Consumes: 无
- Produces: 生产模式是否可用的结论；若不可用，按下方退路修

- [ ] **Step 1: 让 console 转发在非打包场景下都生效**

`src/main/index.ts` 现在是这样：

```ts
  if (process.env.ELECTRON_RENDERER_URL) {
    mainWindow.webContents.on('console-message', (details) => {
      console.log(`[renderer:${details.level}] ${details.message}`)
    })
  }
```

改成：

```ts
  // 开发与「本地跑构建产物」都转发。用 app.isPackaged 而不是
  // ELECTRON_RENDERER_URL 判断 —— 后者在生产模式下不存在，而那正是最需要
  // 看到渲染进程日志的时候（打包后 origin 从 http 变成 file，CSP 与 CORS
  // 的行为都可能不同）。真正打包后没有 stdout，转了也没人看，所以排除。
  if (!app.isPackaged) {
    mainWindow.webContents.on('console-message', (details) => {
      console.log(`[renderer:${details.level}] ${details.message}`)
    })
  }
```

```bash
npm run build
npx electron .
```

Expected: 窗口打开，书架列出已有的书。**终端里能看到渲染进程的日志**。

- [ ] **Step 3: 逐项验证主链路**

按顺序试，每项都盯着终端有没有 `[renderer:error]`：

| # | 操作 | 预期 |
|---|---|---|
| 1 | 看书架 | 4 本书都在、**封面图正常显示**（`app://local/covers/...`） |
| 2 | 打开一本 EPUB | 正文分页渲染、目录能开、能翻页 |
| 3 | 打开 TXT | 正文分页渲染、能翻页 |

| 5 | 改字号 | 生效且位置不跳 |
| 6 | 导入一本新书 | 完整走通 |

- [ ] **Step 4: 记录结论**

- **全部通过** → 记下「生产模式下 `app://` 与 CSP 均正常」，进 Task 2。
- **封面/书籍加载失败，终端报 CORS 或 `Failed to fetch`** → 这是最可能的问题：`file://` 页面在 Chromium 里是**不透明源**，跨源请求受限。走下面的退路。
- **CSP 报违规** → 逐条对照 §2.2 的来源表，确认是哪条在生产 origin 下才触发的。**只允许在表格已列出的放宽项内调整**，`script-src` 不动。

- [ ] **Step 5（仅在失败时）: 退路 —— 让渲染进程也走 app://**

思路：把渲染进程页面本身也由 `app://` 提供，页面 origin 就成了 `app://local`，与书籍资源**同源**，跨源问题自然消失。比关 `webSecurity` 干净得多。

要改三处：

1. `src/main/protocol.ts` 的白名单加一项 `'renderer'`，并把 `out/renderer/` 挂到 `app://local/renderer/`
2. 打包时用 `mainWindow.loadURL('app://local/renderer/index.html')` 替代 `loadFile(...)`
3. `electron.vite.config.ts` 的 renderer `base` 改成相对路径或 `app://local/renderer/`，否则产物里的绝对 `/assets/...` 会 404

> 这条退路改动不算小，**先确认 Step 3 确实失败再走**，别预防性地改。

Expected: 退出 0。

### Task 2: 打包配置与产出

**Files:**
- Create: `electron-builder.yml`
- Modify: `package.json`

**Interfaces:**
- Consumes: `build/icon.ico`（已完成）
- Produces: `npm run build:win`；`release/` 下的安装包与免安装版

- [ ] **Step 1: 装 electron-builder**

```bash
npm i -D electron-builder
```

装完检查 `package.json` 的 `allowScripts` —— npm 11 会拦 postinstall，若 electron-builder 的某个依赖需要下载二进制，按提示放行：

```bash
npm approve-scripts <包名>
```

- [ ] **Step 2: 写 electron-builder.yml**

```yaml
appId: com.bcow0092.markreader
productName: Mark Reader
copyright: Copyright © 2026

directories:
  output: release
  buildResources: build

# 打进包里的只有构建产物与 package.json
files:
  - out/**
  - package.json

win:
  icon: build/icon.ico
  target:
    - target: nsis
      arch: [x64]
    - target: portable
      arch: [x64]

nsis:
  # 一键安装、按用户装 —— 不需要管理员权限，不弹向导
  oneClick: true
  perMachine: false
  # 允许用户改安装目录要配 allowToChangeInstallationDirectory，
  # 一键安装下它是 false 且不可改，这里显式写出来免得后来人误以为漏了
  allowToChangeInstallationDirectory: false
  createDesktopShortcut: true
  createStartMenuShortcut: true
  shortcutName: 马克阅读器
  artifactName: ${productName}-Setup-${version}.${ext}

portable:
  artifactName: ${productName}-Portable-${version}.${ext}
```

> `appId` 用的是仓库所有者的反向域名。它决定 Windows 上应用的身份（升级、卸载都靠它），**发布后不要再改**。
>
> `shortcutName` 用中文，因为那是给用户看的；`productName` 保持 ASCII，因为它是路径。

- [ ] **Step 3: 加脚本**

```bash
npm pkg set scripts.build:win="npm run build && electron-builder --win"
```

- [ ] **Step 4: 打包**


Expected: `release/` 下出现两个产物，形如 `Mark Reader-Setup-0.1.0.exe` 与 `Mark Reader-Portable-0.1.0.exe`。

> 打包要下载 winCodeSign、nsis 等工具，国内可能很慢。若卡住，参照 `.npmrc` 里 `ELECTRON_MIRROR` 的做法加 electron-builder 的镜像（`ELECTRON_BUILDER_BINARIES_MIRROR`）。

产物不该入库。`.gitignore` 里已经有 `release/`，确认一下即可。

### Task 4: CI 接上打包档位

**Files:**
- Modify: `.github/workflows/ci.yml`

**Interfaces:**
- Consumes: Task 2 的 `npm run build:win`
- Produces: `workflow_dispatch` 下产出可下载的安装包

- [ ] **Step 1: 加一个 job**

§6.5 定的档位是「`workflow_dispatch` 跑完整套 + 打包产物验证」。E2E 那部分（Playwright 的 5 条）**不在本里程碑范围**，另起一轮；这里只接打包。

`.github/workflows/ci.yml` 追加：

```yaml
  package:
    # 只手动触发：打包要下载一堆工具、耗时几分钟，日常不该跑
    if: github.event_name == 'workflow_dispatch'
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: npm
      - run: npm ci
      - run: npm run build:win
      - uses: actions/upload-artifact@v4
        with:
          name: mark-reader-windows
          path: release/*.exe
```

- [ ] **Step 2: 本地确认 YAML 合法**

Run: `node -e "const s=require('fs').readFileSync('.github/workflows/ci.yml','utf8'); console.log('行数:', s.split('\n').length)"`
Expected: 能读出来。真正的校验要等推上去跑一次。

